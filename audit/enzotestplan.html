1Principles: change classes, horizons, controls

1.1Classify every change before it lands

The audit's recommendations differ fundamentally in what they are allowed to do to the answer. Testing effort is wasted (or worse, misleading) if a change is held to the wrong standard. Every PR should declare one of three classes, and the class determines which gates in §6 apply:

C0Bitwise-identical expected

Pure code motion that does not alter any floating-point operation or its order: hoisting IdentifySpeciesFields, deleting the per-cell μ file write, guarding debug reductions, removing dead zeroing, timer/instrumentation changes, bounds checks, memory-management fixes (allocatable arrays, scratch pools that preserve values), early returns on provably-zero work (e.g. StarParticleFindAll guard when no Star types exist, nfbcells == 0 return). Gate: bit-for-bit identical outputs at fixed rank count (§3.1).

C1Roundoff-equivalent

Changes that reorder floating-point arithmetic or data ownership but implement the same algorithm: collective fusion, Alltoallv conversions, Morton-sorting particles (reorders CIC summation), load-balancer changes (moves grids → different reduction orders), restored compiler flags (-xAVX, -ip), OpenMP with reductions, sibling-list restructuring. Gate: tolerance-based answer tests at short horizon, statistical equivalence at long horizon (§3.2–3.3).

C2Answer-changing by design

Parameter and algorithm changes whose point is a different (usually better) numerical behavior: RebuildHierarchyCycleSkip, subgrid sizing, MaximumGravityRefinementLevel, INTERPOLATE_LINEAR, INFLUENCE2, the feedback age cutoff, the StarFeedbackSNePerTimestepLimit default fix, dtAcceleration active-zone restriction, RNG seeding. Gate: physical validation against the science metrics (§3.3), reviewed explicitly, then a deliberate re-baseline of the gold answers (§6.3).

Two audit fixes are prerequisites for this plan, not outcomes of it. (1) Seed the feedback RNG (audit §5.1.4): until draw_stochastic is seeded deterministically (per rank, from a run-level seed parameter), stochastic SNe make even C0 comparisons impossible on any run that forms stars. (2) Enable the rebuild sub-phase timers and per-level dt diagnostics (audit §5.5): without them, most of the KPIs in §2.3 cannot be measured. Land both first, as C0/C2-trivial changes validated on runs without star formation.

1.2Comparison horizons: galaxies are chaotic

A FOGGIE galaxy is a chaotic system: roundoff-level perturbations decorrelate individual cell values and particle positions within roughly a local dynamical time. Direct field comparison is therefore only meaningful over short horizons; beyond that, only statistics are comparable. The plan uses three horizons:

  • H1 — a few timesteps (1–5 root steps): direct field and particle comparisons; bitwise for C0, tight relative tolerances (10⁻¹²–10⁻⁸) for C1.
  • H2 — tens of Myr (~10–50 root steps from a production restart): loose field tolerances in stable regions; population statistics begin to be the primary measure.
  • H3 — hundreds of Myr (science-length reruns, milestone-only): purely statistical/physical comparison (§3.3). No expectation of trajectory-level agreement — two C1-equivalent runs will differ here as much as two seeds would.

1.3Controls

  • Fix everything except the change under test: same ICs (store them with the test), same rank count and layout for C0/C1-H1 (reduction order depends on P), same machine partition and node type for benchmarks, same compiler and flags — except when the flags are the change (audit §5.1.6), which is C1.
  • One change per measurement. Tier 0 parameters especially: measure RebuildHierarchyCycleSkip, LoadBalancing = 4, and the subgrid sizing separately before combining, or their effects cannot be attributed.
  • Repeats: ≥3 runs per benchmark configuration; report median and spread. System noise on shared filesystems and networks routinely exceeds 5%; a claimed speedup below the measured spread is not a result.
  • Version the gold data. Every stored answer/baseline records: commit hash, parameter deck, ICs hash, rank count, machine, compiler + flags. A baseline whose provenance is unknown is not a baseline.

2.2Why 5 root steps from a restart

Per the audit's measurement plan (§7.5), a short restart window at production scale captures every cost the audit describes — the 2L subcycle structure, rebuild share, collective counts, feedback costs — without the expense or chaos-divergence of a long rerun. Five steps is long enough to average over rebuild and output cadence, short enough that C1 changes keep the workload (grid counts, particle counts, SF events with a seeded RNG) essentially identical between baseline and candidate, which is what makes A/B timing meaningful.

2.4Acceptance criteria for performance PRs

  • A performance PR states its predicted effect ("reduces rebuild share on B3", "cuts collective count per subcycle by ~2×") and the measured effect on the relevant benchmark, with repeats and spread.
  • No benchmark may regress by more than the measured noise band (2σ of repeats) without an explicit, stated justification.
  • The hydro-only control problem in B2 must be unaffected (within noise) by star/gravity/balance changes — this catches accidental coupling.

3Numerical & physical consistency testing

3.1C0: bitwise regression harness

Procedure. For each C0 PR: run the B2 problem set plus a 2-root-step FOGGIE-bench restart, baseline vs candidate, identical rank count and parameters. Compare every HDF5 output with h5diff (field data, particle data, and attribute values); compare the hierarchy files textually. The gate is zero differences.

  • Bitwise identity in Enzo holds only at fixed processor count and layout — reduction orders change with P. Pin P per test.
  • Runs that form stars require the seeded RNG (§1.1) first; until then, C0 tests run with StarParticleCreation = 0 variants as a partial gate.
  • This harness doubles as the fastest possible reviewer tool: a C0 claim that fails bitwise identity means the change was mis-classified, which is itself the finding.

3.2C1: tolerance-based answer testing (horizon H1–H2)

Framework. Use Enzo's yt-based answer testing: store gold outputs for the B2 set and the 5-step FOGGIE-bench; compare candidate outputs field-by-field and via derived quantities.

  • H1 (1–5 root steps): relative L1/L∞ field errors on density, energies, velocities, metal density; particle position/velocity RMS drift. Start tolerances at 10⁻¹⁰ (H1, few steps, pure FP-reorder changes) and loosen only with justification; record the achieved error so tolerance creep is visible in the ledger.
  • Grid-independent comparison: because C1 changes (especially load balancing and regridding changes) legitimately alter the grid layout, compare on deposited/uniform-resampled fields (yt covering grids at a fixed level) and on global reductions (total mass, metals, energy, momentum by component, star count and total stellar mass), not on per-grid data.
  • H2 (tens of Myr): the field tolerances give way to the statistical metrics of §3.3, evaluated with tight thresholds (the runs are still nearly-identical realizations at this horizon).
  • Conservation invariants (every horizon, every class): total baryon mass, total metal mass (split SNII/SNIa where tracked), total injected feedback energy and momentum (from the feedback accounting already in star_feedback6), and — for non-cosmological control problems — total energy. These must agree to near machine precision regardless of chaos, and they catch real bugs that field tolerances miss.

3.3C2 and long-horizon: physical validation suite

For answer-changing improvements and for any H3 comparison, the question is not "is it the same?" but "is it the same galaxy, physically?" — evaluated with the observables FOGGIE's science depends on. Metrics, evaluated at fixed checkpoint redshifts/times against the baseline run:

Calibrate tolerances with a seed ensemble, once. Run 3–5 realizations of a mid-sized FOGGIE restart differing only in the (newly seeded) feedback RNG seed, to H2 and one to H3. The spread of every §3.3 metric across that ensemble is the natural chaos band: a code change whose effect lies within the band is physically consistent; one outside it needs a physics explanation. This converts "looks similar" into a quantitative, defensible criterion, and the ensemble is reusable for every future C1/C2 change.

The C2 changes with physics content get targeted checks in addition: the feedback age cutoff must reproduce the baseline's total SN count and energy budget to the bookkeeping level (old particles were contributing zeros — so this is really a C1-with-C2-classification safety check); the StarFeedbackSNePerTimestepLimit default fix and RebuildHierarchyCycleSkip must show SFH and CGM metrics inside the ensemble band; MaximumGravityRefinementLevel must pass the gravity tests of §4 plus a DM-profile comparison.

3.4A deliberately boring control

Keep one small cosmological DM+hydro run (no star formation, no feedback — e.g. the nested-cosmology deck with StarParticleCreation = 0) in the answer suite at all times. It is insensitive to the noisiest physics, so it isolates AMR/gravity/communication changes: if it moves outside roundoff when a star-path PR lands, the PR touched something it should not have.

4Gravity-specific accuracy tests

The audit flagged the per-patch Dirichlet gravity scheme (§5.2.2) as an accuracy issue, and several recommended changes (INTERPOLATE_LINEAR, INFLUENCE2, MaximumGravityRefinementLevel, tolerance fix) alter forces by design. These need direct force-quality tests, which also guard the C1 gravity restructurings (Morton sort, deposit refactor, Alltoallv transpose):

  1. Point-mass force accuracy (ProblemType 23, in-tree). RMS and max force error vs. the analytic solution, on a unigrid and with a static refined region so the error is measured across the refinement boundary. Report error vs. radius; the level-boundary discontinuity appears as a spike at the interface. Run before/after each gravity change; C2 gravity changes must reduce (or at worst preserve) the interface error.
  2. Orbit test across a refinement boundary. A two-body/circular-orbit problem in which the orbit crosses a static level boundary; track energy and angular-momentum drift per orbit. This converts the audit's "force jump at level edges" into one number, and directly measures the improvement from INTERPOLATE_LINEAR/INFLUENCE2.
  3. Spurious heating test. An isolated equilibrium halo (DM particles only) spanning 2–3 static levels, evolved for many dynamical times; measure the velocity-dispersion and energy drift of particles binned by radius relative to the level boundaries. This is the artifact FOGGIE stars and DM actually experience; it should shrink with the gravity accuracy bundle and must not grow with any C1 change.
  4. Cosmology cross-check. A small DM-only box: matter power spectrum and halo mass function vs. baseline, tolerance from the roundoff-chaos band. Guards the FFT/transpose and deposit changes at cosmological scales.
  5. Multigrid health. With the iteration-count diagnostic on: distribution of V-cycles per solve and the count of 200-sweep-fallback events on FOGGIE-bench. The fallback count should be ~zero after the tolerance/padding fixes; any nonzero count is logged with the offending grid's dimensions.

6Cadence, gates, and re-baselining policy

6.1Per-PR gate < 1 hr

  • Build (both machine files) + the change-class declaration.
  • C0 PRs: bitwise harness on B2 + 2-step FOGGIE-bench slice (§3.1).
  • C1 PRs: H1 answer tests on B2 with stored tolerances; conservation invariants.
  • All PRs: B1/B2 timing vs. the ledger; predicted-vs-measured statement.

6.2Nightly / weekly automated

  • Nightly: full B2 set (answers + performance) on the current main branch; ledger append; alert on >2σ timing regression or any answer-test failure.
  • Weekly: 5-step FOGGIE-bench (B3) at a reduced-but-representative rank count; the per-level imbalance table and rebuild share tracked over time.

6.3Tier milestones manual review

  • After each audit tier lands: full B3 at production scale (3 repeats), B4 scaling study, §3.3 physical validation at H2 (and H3 after Tier 2), §4 gravity tests.
  • Re-baselining is an explicit, reviewed event: when a C2 change is accepted, its physical-validation report is archived with the decision, the gold answers are regenerated at the new commit, and the ledger records the discontinuity. Gold data is never silently overwritten — the audit found exactly this pattern (undocumented defaults, unrecorded production settings) at the root of several issues.

7Deliverables and automation

  1. run/foggie_bench/ — the versioned FOGGIE-bench deck, restart pointer, launch scripts for Pleiades/Aitken, and the metric-extraction script (one JSON per run).
  2. run/foggie_tests/ — the B2 problem list with parameter decks pinned, the C0 bitwise driver (h5diff wrapper), the C1 answer-test configuration (yt), and the conservation-invariant checker.
  3. Gravity test problems — the orbit-across-boundary and spurious-heating decks (§4.2–4.3; small additions next to the existing TestGravity problems).
  4. The results ledger + plots — CSV/SQLite plus a plotting script tracking the §2.3 KPIs per commit; the audit's four headline numbers (rebuild share, collective time, finest-level imbalance, star-feedback time) on one page.
  5. The seed ensemble (§3.3) — run once after RNG seeding lands; its measured bands checked in as the tolerance file the physical-validation suite reads.
  6. CI hooks — per-PR compile + B2-small in GitHub Actions; nightly/weekly jobs as batch cron on the production machine. The full split of what belongs where is §8.
  7. Prerequisite PRs (from §1.1): RNG seeding; RH sub-phase timers; per-level dt-limiter diagnostic; per-level per-rank work table. These are the plan's foundation and are themselves C0/diagnostic-only.

8What runs in GitHub CI vs. on the supercomputer

The dividing line is not "performance vs. correctness" — it is that hosted CI runners can verify deterministic things (bits, counters, invariants) but cannot measure wall-clock meaningfully, and they top out at a few cores. Everything at production scale, everything timed, and everything touching production data belongs on Pleiades/Aitken.

8.1Mapped to the gates of §6

  • Per-PR gate (§6.1): ~90% CI-implementable — build, class declaration, C0 bitwise, C1 small answer tests, invariants, counter regression. The one exception is the 2-step FOGGIE-bench slice, which needs the machine.
  • Nightly gate (§6.2): splits — answer tests and counters in CI; timing on the machine.
  • Weekly and milestone gates (§6.2–6.3): entirely supercomputer work.

8.2Wiring the two together

NASA HECC security policy makes a self-hosted GitHub runner on Pleiades impractical, so use a pull-based pattern: a cron/batch job on the HPC side pulls main (or a tagged candidate), runs the B3/weekly suite, and pushes its JSON results to a results branch or a small companion repo; a scheduled GitHub Action renders the dashboard and posts commit statuses from that ledger. GitHub orchestrates and displays; the machine only ever initiates outbound connections — no inbound access to HPC is required.

The honest summary: CI can prevent essentially all correctness regressions and all algorithmic-count regressions on every PR — most of the day-to-day protection. What it cannot do is say whether a change actually made FOGGIE faster: every real speedup claim in the audit's tiers is verified by the batch jobs on Pleiades, at weekly-plus-milestone cadence.
